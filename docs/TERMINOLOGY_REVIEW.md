# 用語用法レビュー

## 目的

「標準形」を「面子手」に改めた後の文書を対象に、一般的な麻雀用語の意味と
このリポジトリの形式仕様の意味がずれやすい用法を確認した。ここでいう
「修正」は、実装の識別子を直ちに変更するという意味ではなく、文書・コメント・
公開契約で意味を明示するための提案である。

## 結論

次の4件を優先して修正する。

| 優先度 | 現在の用法 | 推奨する用法 |
|---|---|---|
| 高 | 完成 / 和了形 | 和了可能形（この文書では構造条件に限る） |
| 高 | 1回の改善で完成できる状態 | 1回の有効な遷移で和了可能形に到達できる状態 |
| 中 | 手牌（`Hand`、`Standing`、固定面子を含む場合がある） | 総称としての手牌、内訳は手元牌＋固定面子 |
| 中 | 形を評価できるか（適用可能） | 適用可能（applicable）かどうかを明記する |

「搭子」「ブロック」「面子手」は、直前の「標準形」修正と
[SHANTEN_BLOCKS.md](./SHANTEN_BLOCKS.md) で既にかなり整理されているため、
今回は新しい別名を増やさず、残る4件との境界を明記する。

なお、ここでの修正案はまず文書とLean仕様の説明を対象とする。Go側の公開
フィールド名や契約用語まで同時に確定するには検討が不足しているため、現段階
では変更せず、後述の判断材料を残す。

## 1. 「完成 / 和了形」→「和了可能形」

### 問題

[GLOSSARY.md](./GLOSSARY.md) は「完成 / 和了形 (completion)」を一つの項目に
まとめている。しかし、その定義は「選択した形の必要条件」と「構造だけ」を
扱い、役・フリテン・見逃し・流し満貫を評価しない。一方、一般の「和了」は
通常、ゲーム上の和了成立まで含むため、読者は「`Complete` が真なら和了できる」
と誤解しうる。README でも `completion is -1` と説明しているため、契約の
数値意味とゲーム上の和了を混同しやすい。

### 修正案（採用）

- 用語見出しを **和了可能形** とする。
- ただし本リポジトリでの「和了可能」は、役・フリテン・見逃し・流し満貫等を
  含むゲーム上の和了成立ではなく、**指定した形の構造条件を満たす**という
  限定された意味で使う。
- `Complete` の説明は「指定した形の和了可能形に必要な構造条件」とする。
- README の `completion is -1` は **和了可能形は `-1`** にする。
- 初出では「和了可能形（構造条件のみ）」と併記し、一般の「和了」と区別する。

### 代替案とトレードオフ

- **「完成形」を使う**: 仕様上は安全だが、「何の完成か」が単独では伝わり
  にくく、麻雀用語との接続が弱い。
- **「和了形」を使う**: 麻雀読者には自然だが、ゲーム上の和了成立まで含む
  と読まれやすい。「和了可能形」は目的を示しつつ、構造条件に限定する注記
  を置ける点で折衷になる。

## 2. 「テンパイ」と「改善」

### 問題

[GLOSSARY.md](./GLOSSARY.md) はテンパイを「1回の改善で完成できる状態」と
定義している。「改善」はシャンテン数が下がること、牌を引くこと、牌を交換
することのいずれにも読める。また、Lean の `HandStep` はドローまたは交換を
表すため、実装上の1遷移と麻雀の「受け入れ牌」の説明が対応しない。

### 修正案（採用）

- テンパイを **この仕様で許される1回の有効な遷移の後に、構造上の完成形へ
  到達できる状態** と定義する（用語としては「和了可能形」に合わせる）。
- `HandStep` の説明では「改善」を使わず、**1枚ドローまたは1枚交換による
  遷移** と書く。
- 数値規約は従来どおり「完成 `-1`、テンパイ `0`」とする。
- 実際の麻雀における待ち牌・山に残る枚数・ツモ順を判定する意味ではないと
  注記する。

### 代替案とトレードオフ

- **一般的な「あと1枚で和了」とする**: 読者には最も分かりやすいが、
  `Complete` が和了判定でない問題を再び持ち込む。
- **「距離1」とだけ書く**: Lean の定義とは正確に対応するが、麻雀用語との
  接続が弱く、利用者向け文書として読みにくい。

## 3. 「手牌」「手元牌」「`Standing`」

### 問題

一般の「手牌」は、手元の牌と副露・暗槓などを含む全体を指しうる。
一方、Go 契約の `Standing` は固定面子に含まれない牌だけであり、
`Hand` は抽象モデルとして `counts` と固定面子数を別に持つ。現在の用語集には
この説明があるが、文書ごとに「手牌」が総体・`Standing`・Lean の抽象値の
いずれを指すかを文脈依存で読ませる箇所が残る。

### 修正案（採用）

- **手牌**を総称として残し、必ず次の内訳を使い分ける。
  - **手元牌（standing tiles）**: 固定面子に含まれない牌。Go の `Standing`。
  - **固定面子（fixed melds）**: 入力時点で確定した副露面子・暗槓等。
  - **手牌全体**: 手元牌と固定面子を合わせた計算対象。
- `Hand` を説明するときは「Lean の抽象モデル」と修飾し、実物の全牌を保持する
  麻雀の手牌と同一視しない。
- 「門前」は状態名の翻訳に使わない。暗槓を含むため、`Standing` と門前は
  同義ではない。

### 代替案とトレードオフ

- **`Standing` を「門前牌」と訳す**: 短いが、暗槓を含む契約と衝突する。
- **すべて「手元牌」に統一する**: 誤読は減るが、一般の「手牌」との対応が
  失われ、公開 API の英語名との検索性も下がる。

## 4. 「適用可能（applicable）」

### 問題

「適用可能」は日本語では、役が成立する、計算できる、または実際の局面で
使える、という複数の意味に読める。現在の仕様での `Applicable` は、固定面子
があると七対子・国士無双を最小値の候補から除外するための仕様上の述語であり、
バックエンドの実装能力や、山に牌が残っているかを表さない。用語集には区別が
あるものの、本文だけを読む利用者には境界が弱い。

### 修正案（採用）

- 日本語の対応語を一つに固定せず、初出から **適用可能（applicable）** と
  英語を括弧書きする。
- `Applicable` は「この入力に対して、その形の構造上のシャンテン値を総合値の
  候補に含めるか」を表す、と定義する。
- 「適用不可」は特殊形が固定面子のため対象外である場合に限定する。
- バックエンドが計算機能を持たない場合は **非対応**（`ErrUnsupported`）、
  山の残り枚数や待ちの良し悪しはこの仕様の対象外、と明記する。

### 代替案とトレードオフ

- **「計算対象」とする**: 利用者には直感的だが、`Applicable` との対応が
  弱く、実装能力（capability）との区別を別途覚える必要がある。英語併記なら
  日本語の自然さと識別子の追跡性を両立できる。
- **「合法」とする**: 短いが、麻雀ルール上の合法性を意味してしまい、
  この仕様の構造的な対象判定より強すぎる。

## 変更時の表記ルール

1. `Complete`、`HandStep`、`Applicable` は識別子を変更せず、最初の説明で
   上記の日本語を併記する。
2. 構造条件だけを述べる文では「和了可能形（構造条件のみ）」と書く。
3. 「改善」は単独で使わず、ドロー・交換・遷移のいずれかを明示する。
4. `Standing` は「手元牌」とし、「門前」と同義にしない。
5. `Applicable` は「適用可能（applicable）」と書き、日本語の単独訳に依存
   しない。
6. 「適用不可」と「非対応」を、仕様上の対象外と実装能力不足に使い分ける。

## 優先順位

最初に「完成 / 和了形」と「テンパイ / 改善」を直す。これは数値規約
（和了可能形 `-1`、テンパイ `0`）の読み違いに直結するためである。次に
「手牌 / `Standing`」と「適用可能（applicable）」を直す。これらは入力境界と
エラー分類の誤読を防ぐが、既存の用語集で部分的に説明済みである。

## Go側の再検討に向けた記録

今回、Go側の用語を同時に変更しなかった理由は、`Result.MentsuHand`、
`ShapeResult.Applicable`、`ErrUnsupported` などが公開契約の語彙として既に
結び付いており、日本語文書だけの置換では契約全体の一貫性を判断できないため
である。特に `Applicable` は、形の仕様上の対象外とバックエンドの能力不足を
区別する必要があるため、単純に「計算可能」や「合法」と訳すと意味を狭めたり
広げたりする。

将来Go側を見直す際は、次を判断材料にする。

1. `Result` のフィールド説明で「和了可能形」と数値 `-1` の関係を明示できるか。
2. `Applicable` を日本語化する場合も、`applicable` を併記して仕様上の述語との
   対応を保てるか。
3. APIの識別子を変えずに、README・Goコメント・用語集で意味を揃えられるか。
4. 変更が単なる翻訳ではなく公開契約の意味変更にならないかを確認できるか。

この記録により、今回の文書上の提案と、将来のGo契約の見直しを分離しつつ、
同じ判断基準で再検討できるようにする。
