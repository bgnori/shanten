# `Shanten.lean` レビュー結果

レビュー対象は、依頼時の `shante.lean` に相当するリポジトリ上の
[Shanten.lean](/workspaces/shanten/Shanten.lean) である。レビュー時点では、`lake build Shanten`
は成功した（警告のみ）。

## 概要

牌種、手牌、面子、3種類の形、到達関係、および七対子に関する補助定理は整理されている。
一方で、現在の定義をそのまま「実際の麻雀牌の有限デッキにおけるシャンテン仕様」として
扱うには、以下の2点が未解決である。

| 重大度 | 箇所 | 要約 |
| --- | --- | --- |
| **High** | `Complete`、`HandStep` | 1種類4枚という制約が完成形・ドロー遷移にないため、不可能な5枚目を使う経路を許す |
| **High** | `Hand`、`Complete` | 固定面子の牌内容を保持していないため、固定面子を含む牌種別の容量検証と意味保存を表現できない |

## Findings

### High: 4枚制限が完成形と遷移に反映されていない

`Tile` は赤5を統合した34種類の牌種であり、実際の各牌種には4枚の上限がある。しかし、
[Complete](/workspaces/shanten/Shanten.lean:98) は `HasTiles` によるカウント一致だけを検査し、
各牌種のカウントが4以下であることを要求していない。また、
[HandStep](/workspaces/shanten/Shanten.lean:118) のドロー分岐は、任意の `drawn` について
カウントを1増やすだけで、ドロー後のカウント上限を検査していない。

そのため、例えば既にある牌種を4枚持つ手から同じ牌種をドローし、5枚の牌種を含む完成形へ
到達する証明が可能になる。さらに、`IsThirteenTileHand` の上限条件は初期手にだけ付いており、
[IsShapeShanten](/workspaces/shanten/Shanten.lean:146) や `ReachesCompletion` の全経路へは
伝播しない。結果として、正当な13枚手のシャンテン値が、実在しない完成形を経由して小さく
なる可能性がある。

これは「見えている牌の枚数を考慮しない」こととは別の問題である。残り牌の可用性を考慮しない
場合でも、完成形そのものが4枚制限を破ってはならない。

**推奨修正**

* `Complete` の全形に、`∀ tile, hand.counts tile ≤ 4`（固定面子を別表現にする場合は合算値）
  を要求する。
* `HandStep` のドロー分岐で、`after` が有効なカウント制約を満たすことを要求する。
* 入力制約と到達関係で同じ不変条件を使えるよう、`ValidCounts` などの共有述語を導入する。
* 4枚制限を変更しないことを意図する場合は、少なくともこのモデルが「無限供給の構造仕様」
  であり、実デッキ仕様ではないことをモジュールコメントと計画文書に明記する。

### High: 固定面子の牌内容がモデルに存在しない

[Hand](/workspaces/shanten/Shanten.lean:24) は `counts` と `fixedMelds : Nat` だけを持ち、
固定面子がどの牌を消費しているかを記録しない。`Complete .mentsu` は
`melds.length + hand.fixedMelds = 4` だけを見ており、固定面子の牌を
`HasTiles` の対象に含めていない。

この設計では、例えば固定面子に同じ牌種が何枚含まれているか、暗槓が4枚を消費しているか、
手牌と固定面子を合算した牌種の上限を超えていないかを表現できない。したがって、READMEで
定めている「standing tiles と fixed melds の合計で容量を検査する」という契約や、赤5を
統合しても面子構成を壊さないという計画上の性質を、このLeanモデルから証明できない。

また、固定面子を単なる個数に抽象化したままでは、固定面子の牌内容に依存する不正入力を
区別できない。`fixedMelds = 1` の2つの手が、牌の構成上は異なるのに同じ状態として扱われる。

**推奨修正**

* `Hand` に固定面子のリスト（必要なら、順子・刻子・槓を区別する型）を保持させる。
* 固定面子から牌マルチセットを計算し、standing counts と合算したカウントで容量を検証する。
* `fixedMelds` はリスト長から導出するか、保持するならリスト長との一致を不変条件にする。
* 槓を1面子として数える一方、牌の消費数は4枚であることを明示する。

## 補足

* [IsThirteenTileHand](/workspaces/shanten/Shanten.lean:224) は初期手について固定面子数0、
  牌数13、各牌種4枚以下を要求しており、単独の入力述語としては妥当である。ただし、
  その不変条件が `ReachesCompletion` の定義に組み込まれていないため、上記のHigh findingを
  解消しない。
* [ShapeShanten](/workspaces/shanten/Shanten.lean:171) と [OverallShanten](/workspaces/shanten/Shanten.lean:207)
  は `noncomputable` な存在選択に基づく定義である。これは宣言的仕様としては許容できるが、
  計算可能なシャンテン計算器やGo実装の基準関数として直接利用するには、有限探索関数と
  その仕様との同値証明が別途必要である。
* ビルド時には未使用の`simp`引数、不要な`<;>`、`Mathlib`のモジュール形式に関する警告が
  出ている。現時点でビルドを失敗させるものではなく、上記の意味論上の問題より優先度は低い。

## 対応方針

固定面子の牌内容を `Hand` に追加する案（C案）は、4枚制限を表現するうえで本質的である。
ただし、現時点の主な対象は七対子のシャンテン関係であり、面子手と国士無双のシャンテン
関係およびその証明がまだ追加されていない。この段階でC案を4枚制限の修正として導入すると、
未完成の形の仕様化と手牌モデルの大規模変更が同時に発生し、変更の因果関係と検証範囲が不明確に
なる。そのため、C案は今回の修正には含めない。

対応は次の順序で進める。

1. **B案を先に実装する。** `Shanten.lean` に `ValidCounts` を導入し、開始手と完成形、
   および `HandStep` のドロー遷移後状態に4枚制限を要求する。これにより、現行の34種
   モデルの範囲内で、4枚制限が完成形とドロー遷移の両方に反映される。
2. **3形のシャンテン関係を完成させる。** 七対子に加えて、面子手と国士無双の完成形・
   到達関係・シャンテン値の定義と、計算可能な関係との証明を追加する。
3. **C案へ戻る。** 3形の関係と証明が揃った段階で、固定面子を牌内容付きで表現する
   必要性を再評価し、standing tiles と固定面子を合算した容量検証へモデルを拡張する。

この順序では、B案を今回のHigh findingに対する完了条件とし、C案は面子手・国士無双を
含む全体モデルの拡張として別の変更単位にする。C案を導入する際には、槓の牌消費数、
固定面子の種類、赤5を統合した34種モデルと37種入力契約との境界も併せて確定する。

## 検証

実行したコマンド:

```text
lake build Shanten
```

結果は成功（exit code 0）。今回のレビューではソースの変更は行っていない。
