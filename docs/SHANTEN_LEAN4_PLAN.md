# シャンテン計算のLean4正当化計画

## 目的と範囲

この文書は、`shanten-submodule` の数値計算ロジックをLean4で定義・証明し、
その仕様に一致するGo実装を後段で提供するための計画である。現段階では計画の
文書化のみを行い、Leanソース、Go計算器、アダプター、ビルド設定の実装は開始
しない。

Go側の型・入出力・エラーの境界は
[外部シャンテン計算モジュール契約](./SHANTEN_EXTERNAL_MODULE.md) と
サブモジュールの [README](../modules/shanten/README.md) を正とする。Lean側は
この契約の意味をより厳密な数学的モデルとして定義し、Go側はそのモデルに対する
実行可能な実装および適合テストとして扱う。

## 成果物

最終的に、次の成果物を段階的に作成する。

1. Lean4プロジェクト（独立した検証用ディレクトリまたは専用リポジトリ）
2. 牌種、赤5の正規化、手牌、面子、3種類の形の形式モデル
3. 不正入力を排除する検証述語と、正規化が意味を変えないことの証明
4. 一般形・七対子・国士無双のシャンテン数の定義
5. 各定義と実装可能な探索アルゴリズムの一致証明
6. Go実装がLean仕様を満たすことを確認する、共有ベクトルを使った適合テスト
7. 証明済み仕様からGo実装へ移植する際の対応表とレビュー手順

LeanからGoコードを自動抽出することは初期方針にしない。抽出可能性よりも証明の
可読性と、Goランタイム・既存型との統合容易性を優先する。将来、抽出が有益と
判断できた場合は、別途方式を評価する。

## 固定する契約

以下は実装前に変更しない前提である。

- 牌種は赤5を分離した37種で表現し、計算時は色・数の通常5へ合算する。
- `Counts37` の順序、牌種ごとの容量、赤5の対応関係は既存契約に従う。
- 副露面子は固定面子であり、暗槓も含めて七対子・国士無双を不適用とする。
- 一般形は常に適用可能、テンパイは`0`、和了は`-1`である。
- 固定面子がない場合の総合値は、一般形・七対子・国士無双の適用可能な値の最小値
  である。
- 不正入力は結果に変換せずエラーとし、対象外の特殊形は最小値に含めない。
- 同一の正規化済み入力に対する結果は決定的である。

契約の変更が必要になった場合は、証明を継ぎ足す前に契約バージョンと本計画の
対応箇所を見直す。

## 対応順序に関する決定

現在のLeanモデルでは七対子に関する補助定理が先行しており、面子手と国士無双の
シャンテン関係およびその証明は未完成である。固定面子の牌内容を `Hand` に持たせる
C案は4枚制限を完全に表現するための本質的な拡張だが、現段階で導入すると、未完成の
3形の仕様化と手牌モデルの大規模変更が同時になる。そのため、C案を4枚制限への当面の
修正としては採用しない。

次の順序を計画上の対応方針として固定する。

1. **B案: 共有不変条件の導入**
   - `ValidCounts` を定義し、入力（`IsThirteenTileHand`）と完成形の共有不変条件にする。
   - `HandStep` のドロー遷移後状態に `ValidCounts` を要求する。
   - 4枚ちょうどの牌を5枚目として引く遷移や、5枚を含む完成形が排除されることをLeanの型付き命題として維持する。
2. **面子手・国士無双のシャンテン関係の追加**
   - 両形の完成形と到達関係を定義する。
   - シャンテン値と有限探索または計算可能な関係との一致を証明する。
   - 3形の適用可能性と総合最小値への反映を証明する。
3. **C案: 固定面子の牌内容付きモデルへの拡張**
   - 固定面子を個数ではなく、牌内容を持つ構造として表現する。
   - standing tiles と固定面子を合算した牌種別カウントで容量を検証する。
   - 槓の面子数と牌の消費数、赤5の正規化、および37種入力契約との境界を確定する。

したがって、B案の完了を今回の4枚制限の対応完了とし、C案は3形のシャンテン関係が
揃った後に別の変更単位として実施する。C案を開始する際は、本計画のPhase 1の
固定面子・容量検証の項目を更新してから実装に着手する。

## 段階計画

### Phase 0: 仕様の凍結とLean環境の決定

- 37種のインデックス、容量、通常5への写像を表にして仕様化する。
- `m = 0..4` の固定面子数と、門前牌数 `13 - 3*m` / `14 - 3*m` の意味を固定する。
- Lean4およびMathlibの採用バージョン、ビルド方法、CIでの再現方法を決める。
- 既存Go契約との用語差（standing、fixed meld、shape、applicable）を対応表にする。

**完了条件:** 曖昧な入力条件、牌の順序、赤5の意味、出力の対象外規則が残って
いないこと。Leanプロジェクトの最小ビルドが再現できること。

### Phase 1: 基礎モデルと入力不変条件

- 牌種を有限型または有限インデックスとして定義し、37種の全射・単射性を証明する。
- 赤5を通常5へ写す正規化関数と、正規化後の34種相当のランク表現を定義する。
- カウントを自然数ベクトルとして表し、牌種容量、非負性、総牌数を述語化する。
- チー、ポン、暗槓、大明槓、加槓の構造と、槓を1面子として数える規則を定義する。
- 「門前牌と固定面子の合計が契約上の入力である」ことを型または検証述語で表す。

証明する主な性質:

- 赤5の正規化は牌の総数を保存する。
- 正規化は赤5の位置以外の面子構成を変えない。
- 有効な入力では各牌種の容量を超えない。
- 固定面子の構成は正規化後に契約の形（順子、刻子、槓）を満たす。

### Phase 2: 形の数学的定義

まずアルゴリズムに依存しない、集合または有限構造に基づく仕様を定義する。

- **一般形:** 固定面子数を考慮し、残りを面子、搭子、雀頭へ分解する構造と、
  その不足量からシャンテン値を定義する。
- **七対子:** 7種類の異なる対と、必要な重複種類数を表す構造を定義する。
- **国士無双:** 13種類の么九牌・字牌の被覆数と、そのうちの対の有無を定義する。
- 適用可能性を固定面子数から定義し、対象外の値を総合最小値から除外する。
- 和了を`-1`、テンパイを`0`とするオフセットを明示的に定義する。

この段階では「よく使われる再帰式」を先に正とせず、完成形を特徴付ける仕様を
正とする。これにより、後続の探索実装が別の枝刈りや走査順を使っても、同じ値を
返すことを証明できる。

### Phase 3: 計算可能な探索と正当性証明

一般形の計算は、実行用計算器とLean上の証明で同じ探索状態・遷移・評価を使う
**DPベースの有限探索**を基準実装とする。単に全手牌を列挙するのではなく、牌種を
順に処理する面子分解DPを共通部品として定義する。

- 一般形について、牌種を順に処理する有限探索（面子・搭子・雀頭の選択）を定義する。
- 七対子・国士無双について、カウントから直接計算する有限関数を定義する。
- 一般形の探索状態に、処理済み牌種、残り牌、面子数、搭子数、雀頭の有無、
  固定面子数などを持たせる。
- 枝刈りは、下界を証明できる場合にのみ導入する。初期版では全探索を基準実装とし、
  性能最適化を証明の後段へ分離する。
- 各計算関数が仕様上の最小値を返すこと（soundness と completeness）を証明する。

特に一般形では、次を別々に証明する。

1. 探索が返した分解は、実際に入力を被覆する有効な分解である。
2. 任意の有効な分解が、探索のどこかの枝で表現される。
3. 枝ごとの評価値の最小値が、定義した一般形シャンテン数に一致する。

#### DPと実行用計算器の共通化

DPは、次の3層に分ける。

1. **共有データ層**
   - 正規化済み34種の牌カウント
   - 牌種の順序と次牌種の取得
   - 面子（順子・刻子）、搭子、雀頭の候補判定
   - 固定面子数と必要な非固定面子数
2. **共有探索層**
   - `SearchState` 相当の状態
   - 状態からの有限な遷移
   - メモ化可能な状態キー
   - 状態の評価値と最小値演算
3. **境界層**
   - Leanでは仕様命題と証明
   - Goでは入力検証、配列・キャッシュ、エラー変換

共有探索層は、まずLeanで実行可能な純粋関数として定義する。その関数と同じ
状態遷移をGoへ移植し、後からGo固有の配列・キャッシュ最適化を加える。Go実装を
Leanの証明済み関数から自動抽出することは前提にしないが、状態・遷移・評価の
対応表を維持する。

#### 探索状態

一般形の最小状態は、次の情報を持つ。

```text
処理済みの牌種位置
各牌種の残りカウント
確定した面子数（固定面子を含む）
搭子数
雀頭を確定したかどうか
```

固定面子数 `m` は遷移中に変更せず、完成条件では必要な面子数を `4 - m` とする。
搭子数は、面子数と合算して4組を超えないように評価時に制限する。

状態遷移は、各牌種について次の選択肢を列挙する。

- 牌を面子・搭子・雀頭に使わず残す
- 刻子を取る
- 順子を取る
- 対子を雀頭として取る
- 対子または連続牌を搭子として取る

各遷移が入力カウントを超えないこと、牌種位置が進むこと、面子・搭子・雀頭の
上限を超えないことを不変条件とする。

この共有層の最初の実装は
[`Shanten/Standard.lean`](../Shanten/Standard.lean) に置く。ここでは既に、
DP状態の骨格、標準形の目標牌姿、目標に対する牌種ごとの不足枚数を定義している。
次の実装単位で、残りカウントを状態へ追加し、各選択肢の遷移とメモ化可能な
評価関数を実装する。

現在は、有効な標準形ターゲットを有限集合として列挙し、その最小距離が
`IsShapeShanten` と一致する実行可能な参照探索を用意している。ただし、これは
全ターゲット候補を列挙する方式であり、状態遷移をメモ化する実運用向けDPではない。
既存のブロック探索は手牌に含まれるブロックのみを選ぶため、牌不足を評価する
標準形シャンテン探索の完全性を単独では与えない。次のDP実装では、選択した
ブロックの不足牌数を評価に反映し、この参照探索との一致を証明する必要がある。

#### 健全性・完全性

探索結果と宣言的仕様の対応は、次の順で証明する。

1. `searchStep_sound`: 各DP遷移が実際の牌の消費に対応する。
2. `searchResult_sound`: DPが返した分解が有効な標準形の分解である。
3. `searchResult_complete`: 任意の有効な分解が、DPのいずれかの枝で列挙される。
4. `searchValue_eq_specification`: DPの最小評価値が標準形の仕様上の値に一致する。

この対応を通して、DPの値から

```lean
∃ distance : Nat, distance ≤ 9 ∧
  ReachesCompletion Complete .standard hand distance
```

を構成する。既存の
[`standardShanten_le_eight_of_completion_bound`](../Shanten/Bounds.lean) は、この
到達性補題を受け取る最終段階として再利用する。

固定面子がある場合は、[`HandStep`](../Shanten/Specification.lean) の
`fixedMelds` 不変条件とDPの固定面子数を対応させる。`fixedMelds > 0` なら七対子・
国士無双が不適用であることを使い、標準形の上限から総合値の上限を導出する。

#### 証明と計算器の検証順序

最初から枝刈りや高度なキャッシュを証明対象にしない。次の順序で実装する。

1. 枝刈りのない、明示的な有限DPをLeanで定義する。
2. 小さな牌種モデルで全枝を列挙し、仕様との一致を確認する。
3. 一般の34種モデルで健全性・完全性を証明する。
4. DPが常に9手以内の標準形候補を返すことを証明する。
5. 同じDPをGoの基準実装へ移植する。
6. キャッシュ、対称性、下界による枝刈りを追加し、基準DPとの一致を確認する。

最適化版が基準DPと同じ値を返すことを別途確認し、最適化の正しさを標準形仕様の
証明に混ぜない。

### Phase 4: 総合結果とエラー境界

- 3形の値と適用可能性から`Result`相当の数学的構造を定義する。
- `Shanten`が適用可能な値の最小値であることを定理化する。
- 不適用時の特殊形フィールドが`0`であり、最小値へ影響しないことを定理化する。
- 不正入力、未対応機能、計算失敗、結果不整合をLean仕様上の分類として整理する。

Leanの純粋な計算仕様と、Goの`error`表現は同一型にしない。Leanでは入力検証
失敗と計算結果を合成型で表し、Goでは既存の`ErrInvalidCount`等へ対応付ける。

### Phase 5: Go移植と適合性確認

- Lean仕様の各関数に対して、Goの型・関数・テストケースの対応表を作る。
- まず証明と同じ単純な探索をGoへ移植し、最適化は値一致テストの後に行う。
- Leanで生成または列挙した有限ケースを、言語間で安定したJSONまたは表形式の
  fixtureとして共有する。
- Go実装について、入力検証、赤5正規化、3形の値、適用可能性、総合最小値、エラー分類を
  fixtureとプロパティテストで確認する。
- 最適化版は基準実装と同じfixtureを全件通過させ、可能ならランダム生成ケースも比較する。

「Leanが証明した」ことと「Go実装がその定理を満たす」ことは別の主張である。
後者は、共有fixture、独立した基準実装との比較、Go側の不変条件テストを組み合わせて
確認する。

## 証明・テスト戦略

### 小さい有限領域での網羅確認

- 牌種を減らしたモデルや少数牌のモデルで、全入力列挙と定義の一致を確認する。
- 固定面子数、13枚/14枚、赤5の有無、七対子・国士無双の境界を重点的に列挙する。
- 典型的な和了、テンパイ、1シャンテン、七対子、国士無双、面子手を代表例にする。

### 境界・反例

- 牌種容量ちょうど、容量超過、負数（Go入力時）、面子数5以上。
- 門前牌数の不整合、赤5を通常5へ合算した後の容量超過。
- 順子でないチー、3枚でない刻子、4枚でない槓、加槓の二重入力。
- 暗槓によって特殊形を不適用にするケース。
- すべての特殊形が不適用または一般形だけが適用されるケース。

### 不変条件

証明とテストで、少なくとも次を維持する。

- 入力を正規化しても牌数と結果の意味が変わらない。
- 入力の順序や赤5の配置だけでは結果が変わらない。
- 総合シャンテン値が個別の適用可能な値より大きくならない。
- 結果がエラーでない場合、すべての適用可能な値は`-1`以上である。
- 同じ入力を繰り返しても同じ結果になり、入力を変更しない。

## 最適化の扱い

面子・搭子・雀頭を処理するDP自体を、最初から実行用計算器と証明の共有基盤にする。
ただし、初期の証明対象は枝刈りのない明示的なDPとし、次の最適化は基準DPの値一致を
確認した後に導入する。

- 状態のメモ化と配列キー化
- 対称性による重複状態の除去
- 下界に基づく枝刈り
- 既知のシャンテン表やキャッシュ
- Goでの割り当て削減、ビット表現、並列化

最適化は仕様を変更しない。各最適化について、基準DPまたは仕様関数と同値である
ことを証明するか、全fixtureと独立基準実装との比較で検証する。証明負荷が過大な
枝刈りは、実行用の最適化として導入しても、初期のLean証明対象には含めない。

## リポジトリとCIの方針

配置は、親リポジトリのGoモジュールへLean依存を持ち込まず、次のいずれかをPhase 0
で決定する。

1. `shanten-submodule` 内にLeanプロジェクトを置く。
2. Lean検証を専用リポジトリへ分離し、親からfixtureとバージョンを参照する。

どちらの場合も、Leanのビルド・定理検証とGoのテストをCIで独立して実行し、片方の
成功をもう片方の証明とみなさない。Lean・Mathlibのバージョンは固定し、fixtureには
仕様バージョンと生成元コミットを記録する。

## 完了条件

実装開始前に本計画で合意すべき事項:

- Leanプロジェクトの配置とバージョン
- 形の数学的定義（特に一般形の分解とシャンテン値）
- エラー境界をLean仕様とGo契約へ対応付ける方法
- fixtureの形式、生成者、バージョン管理方針
- 初期版で証明する範囲と、最適化を後段へ送る範囲

計画の最終的な完了は、次を満たした時点とする。

- Leanで3形と総合値の定義および正当性定理がビルドできる。
- 正常系・境界系・不正系の共有fixtureがある。
- Go実装がfixtureと契約テストを通過する。
- Go実装の各計算経路がLean仕様の対応箇所に追跡できる。
- 最適化を追加しても基準実装・fixture・証明済み仕様との不一致がない。
